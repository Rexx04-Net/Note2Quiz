# FYP2 Technical Specification & Prompt
# Automated Syllabus & Timetable Revision Engine
# Project: Note2Quiz

## 1. Role and Task

You are an expert Full-Stack Developer specializing in:

- Flutter / Dart
- Python / Flask
- MongoDB
- APScheduler
- Google Gemini API
- Google Calendar API
- OAuth 2.0
- SMTP email
- Deep linking

Your task is to generate a complete, modular, production-oriented implementation of the **Automated Syllabus & Timetable Revision Engine** for the educational application **Note2Quiz**.

This specification is intended to be used as a master prompt for an AI coding agent.

IMPORTANT:
- Use the existing Note2Quiz backend architecture where possible.
- The backend framework is **Flask**, not FastAPI.
- Do not replace existing project architecture unless explicitly required.
- Generate code incrementally and keep each module independently testable.
- Do not silently invent APIs, database fields, routes, credentials, or project files that are not defined here.
- If an implementation detail is genuinely ambiguous, choose a reasonable default and clearly document it.

## 2. System Objective

The feature must allow a student to:

1. Select a course/notebook.
2. Upload a syllabus PDF.
3. Enter semester and timetable information.
4. Send the syllabus and configuration to the Flask backend.
5. Use Gemini to extract weekly lecture topics.
6. Validate and normalize the AI-generated result.
7. Generate a weekly revision schedule.
8. Store the automation and schedule in MongoDB.
9. Optionally create a dedicated Google Calendar for the course.
10. Create weekly calendar events.
11. Run a background scheduler that detects due revision notifications.
12. Send a notification email containing a Note2Quiz deep link.
13. Open the corresponding quiz/revision screen through the mobile app.

The complete flow is:

Student
    ↓
Flutter UI
    ↓
Flask REST API
    ↓
Syllabus Parser
    ↓
Gemini
    ↓
Validation / Normalization
    ↓
MongoDB
    ↓
Schedule Calculator
    ↓
Google Calendar
    ↓
APScheduler
    ↓
Notification Service
    ↓
Email
    ↓
note2quiz:// deep link
    ↓
Quiz / Revision Screen

# 3. Architecture Rules

## 3.1 Technology

Frontend:
- Flutter
- Dart
- file_picker
- app_links
- http

Backend:
- Python
- Flask
- Flask-CORS
- Werkzeug (for file uploads)
- pymongo
- APScheduler
- pytz or zoneinfo
- Google APIs
- SMTP

Database:
- MongoDB

AI:
- Google Gemini API
- Use a currently supported Gemini model configured through an environment variable.
- Do not hard-code a model name in business logic.

## 3.2 Timezone Safety

All scheduling operations must use timezone-aware datetimes.

Default timezone:

    Asia/Kuala_Lumpur

Rules:
- Never compare naive and timezone-aware datetimes.
- Store timestamps in UTC in MongoDB where practical.
- Preserve the user's configured timezone.
- Convert UTC timestamps to the user's timezone when displaying them.
- All timetable calculations must use the configured timezone.

## 3.3 Course Isolation

Every automation belongs to exactly one:

- user
- notebook
- course

Every schedule item, calendar event, notification, and deep link must contain enough information to identify the correct notebook/course.

Required identifiers:

    notebook_id
    course_name
    week_number

Never allow one course's automation to modify another course's schedule.

## 3.4 Idempotency

All background operations must be safe to retry.

Examples:
- Do not create duplicate calendar events.
- Do not send the same notification repeatedly.
- Do not create duplicate course automations.
- Do not regenerate an existing quiz unless explicitly requested.

Use database state transitions and stable identifiers.

Recommended notification states:

    PENDING
    PROCESSING
    COMPLETED
    FAILED

# 4. MongoDB Data Model

## 4.1 Collection

Collection name:

    course_automations

## 4.2 Document

Recommended structure:

{
    "_id": ObjectId,
    "notebook_id": String,
    "user_email": String,
    "course_name": String,
    "timezone": "Asia/Kuala_Lumpur",

    "semester_config": {
        "start_date": ISODate,
        "total_weeks": Integer,
        "has_break_week": Boolean
    },

    "timetable": {
        "day_of_week": String,
        "class_start_time": String,
        "class_end_time": String
    },

    "syllabus_metadata": {
        "filename": String,
        "source": "gemini" | "fallback",
        "parsed_at": ISODate
    },

    "sub_calendar_details": {
        "provider": "google",
        "calendar_id": String,
        "calendar_name": String
    },

    "weekly_schedule": [
        {
            "week_number": Integer,
            "topic_title": String,
            "key_concepts": [String],

            "class_start_timestamp": ISODate,
            "class_end_timestamp": ISODate,

            "revision_trigger_timestamp": ISODate,

            "status": "PENDING" | "PROCESSING" | "COMPLETED" | "FAILED",

            "quiz_id": String | null,

            "calendar_event_id": String | null,

            "notification_sent_at": ISODate | null,
            "completed_at": ISODate | null,
            "last_error": String | null
        }
    ],

    "created_at": ISODate,
    "updated_at": ISODate
}

## 4.3 Indexes

Create:

1. Unique compound index:

    notebook_id + user_email

2. Query index for due schedules:

    weekly_schedule.status
    weekly_schedule.revision_trigger_timestamp

3. Optional indexes for:

    user_email
    course_name
    updated_at

The implementation must avoid creating duplicate indexes on application startup.

# 5. Gemini Syllabus Parsing Service

File:

    backend/services/syllabus_parser.py

## 5.1 Input

The parser must accept:

- PDF byte stream
- total_weeks
- course_name

## 5.2 Gemini Requirements

Gemini must be instructed to:

- Analyze the syllabus.
- Identify weekly lecture topics.
- Map topics to week numbers.
- Extract important key concepts.
- Return structured JSON only.
- Never invent a topic when the syllabus provides insufficient evidence.
- Mark uncertain topics appropriately.

Expected output:

{
    "course_name": "...",
    "weekly_topics": [
        {
            "week_number": 1,
            "topic_title": "...",
            "key_concepts": ["...", "..."]
        }
    ]
}

## 5.3 Validation

Never insert raw Gemini output directly into MongoDB.

Perform validation:

1. JSON parsing.
2. Dictionary schema validation.
3. Week number validation.
4. Duplicate week detection.
5. Expected total-week validation.
6. Topic title validation.
7. Key concept normalization.

If Gemini returns fewer or more weeks than expected:
- Do not silently discard data.
- Apply a documented normalization strategy.
- Record warnings.
- Preserve the original AI result where appropriate.

## 5.4 Failure Handling

If Gemini fails:

- Catch API errors.
- Catch malformed JSON.
- Catch validation errors.
- Prevent the backend from crashing.
- Generate a deterministic fallback schedule only when necessary.
- Mark the source as:

    fallback

- Return a warning to the frontend.

The UI must be able to tell the user that fallback data was generated.

# 6. Schedule Calculation

File:

    backend/utils/scheduler_utils.py

## 6.1 Inputs

The calculation utility must accept:

- semester start date
- total_weeks
- class day of week
- class start time
- class end time
- timezone
- has_break_week

## 6.2 Output

Return a list of timezone-aware schedule objects containing:

- week number
- class start timestamp
- class end timestamp
- revision trigger timestamp

## 6.3 Week Calculation

Example:

Semester start:

    Monday

Class day:

    Monday

Class:

    16:00 - 18:00

Then:

Week 1:
    class start = Monday 16:00
    class end   = Monday 18:00

Week 2:
    class start = following Monday 16:00
    class end   = following Monday 18:00

Continue until the configured semester duration is reached.

## 6.4 Mid-Term Break

If:

    has_break_week = true

insert exactly one skipped calendar week.

Example:

Week 6
Week 7
BREAK
Week 8

The implementation must define whether "week_number" represents academic week or calendar week and use that definition consistently.

Recommended:

- week_number = academic teaching week
- break week is not assigned a teaching week number

## 6.5 Revision Trigger

Do not automatically assume that revision starts exactly at class end.

Use a configurable revision delay.

Default:

    revision_delay_hours = 24

Therefore:

class_end_timestamp
    +
revision_delay_hours
    =
revision_trigger_timestamp

The delay must be configurable in the backend.

# 7. Google Calendar Integration

File:

    backend/services/calendar_service.py

## 7.1 Authentication

Use Google OAuth 2.0.

Requirements:
- Store credentials securely.
- Never hard-code client secrets.
- Use environment variables/configuration.
- Handle expired access tokens using refresh tokens.
- Do not expose tokens to Flutter.

## 7.2 Dedicated Calendar

Create or reuse a dedicated calendar:

    Note2Quiz - [course_name]

Do not create a new duplicate calendar every time the automation is submitted.

Store:

    calendar_id

in MongoDB.

## 7.3 Calendar Events

For every weekly schedule item, create one event.

Event must contain:

Title:

    Note2Quiz Revision - Week [N] - [Topic]

Description must contain:

    notebook_id
    course_name
    week_number
    deep link

Deep link format:

    note2quiz://revision?notebook_id={notebook_id}&week_number={week_number}

Store the returned:

    calendar_event_id

in MongoDB.

## 7.4 Event Idempotency

Before creating an event:
- Check whether the schedule item already has a calendar_event_id.
- If it does, update the existing event instead of creating another one.
- If the event no longer exists, recreate it and update the stored ID.

Use stable event metadata where possible.

Required Google Calendar private metadata:

    notebook_id
    course_name
    week_number

# 8. Notification Scheduler

File:

    backend/jobs/notifier.py

## 8.1 Scheduler

Use:

    APScheduler BackgroundScheduler

Run the worker every:

    1 minute

The scheduler must start once when the Flask application starts and shut down cleanly when the application stops.

Do not create multiple scheduler instances during development reloads.

## 8.2 Query

Find schedule items where:

    status = PENDING
    revision_trigger_timestamp <= now

Only process schedules belonging to valid active automations.

## 8.3 Atomic Claim

Before sending a notification:

PENDING
    ↓
PROCESSING

The state transition must be protected against multiple workers processing the same schedule item.

If another worker already changed the item to PROCESSING, skip it.

## 8.4 Send Notification

Use SMTP to send an HTML email.

The email must contain:

- course name
- week number
- topic title
- revision message
- deep-link button

Example deep link:

    note2quiz://revision?notebook_id=ABC&week_number=5

## 8.5 Completion

After successful email delivery:

    PROCESSING
        ↓
    COMPLETED

Set:

    notification_sent_at
    completed_at

If sending fails:

    PROCESSING
        ↓
    FAILED

Store:

    last_error

The system must allow failed notifications to be retried safely.
